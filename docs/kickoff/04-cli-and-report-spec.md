# Alibi: CLI and Report Spec

This fills the frontend-spec slot. Alibi has no web UI, so the surfaces a human touches are the CLI, the report, and the figure. Same substitution Lockstep settled on, and for the same reason: specifying the surface that exists beats specifying one that does not.

Design goal for all three surfaces: a reader who has never seen the repo can go from `git clone` to checking a published number in under five minutes, without a GPU.

---

## 1. CLI

Single dispatcher, `alibi`, subcommands underneath. Every command takes `--run-id` or generates one, and every command writes what it did into the run directory.

```
alibi data build                    Build MBPP + MBPP+ join, write split manifest
alibi data check                    Sanity: base model visible pass rate, cheat headroom
alibi train --arm {a0,a1,a2,a3} --seed N
alibi eval --run-id R               Score a finished run's checkpoints against held-out
alibi report                        Build the report and the figure from index.json
alibi verify [--no-gpu]             Recompute every published number, exit non-zero on mismatch
alibi replay --run-id R             Re-derive metrics from stored artifacts, assert cache 100%
```

**Global flags:** `--config`, `--dry-run`, `--allow-monitor-misses` (off by default, loud when on).

**Conventions:**
- Every command prints its resolved config hash on the first line and its run id on the last.
- Nothing writes into `artifacts/` without also writing `env.lock`.
- `--dry-run` on `train` runs three steps with two prompts and a stub monitor. This is the command used to check the loop is wired, and it must stay working all week.
- Exit codes: 0 success, 1 assertion or mismatch, 2 configuration error, 3 sandbox unavailable.

**`alibi data check` is the day-one gate.** It reports the base model's visible pass rate, held-out pass rate, and the fraction of problems where hardcoding the visible asserts would pass. If that last number is not high, the environment does not incentivise cheating and the PRD's H1 is dead before any GPU time is spent.

## 2. Console output

Training prints one line per step, fixed width, no progress-bar spam in logs:

```
step 042 | arm a1 seed 1 | reward 0.61 | vis 0.78 | held 0.19 | oracle 0.59 | flag 0.22 | gap 0.37 | kl 0.031 | cache 0.94
```

Every field in that line is a published metric. Anything not published does not go in the line. If a number in the console cannot be recomputed by `alibi verify`, one of the two is wrong.

Warnings are loud and single-line, prefixed `WARN`. The three that matter:
- monitor cache miss during a replay
- dirty git tree at run start
- sandbox control unavailable on this host, with the specific control named

## 3. The figure

One figure. Not a dashboard.

- x: training step
- y: obfuscation gap
- three lines, A0, A1, A2, one colour each, consistent across every artifact in the repo
- shaded band per line: min to max across seeds, not a standard error, because n=3
- a horizontal reference at gap = 0
- caption states the model, step count, seeds, lambda, and the exact metric definition

Secondary figures, only if they earn it: oracle cheat rate and monitor flag rate as separate panels, since the gap alone hides whether it opened by cheating more or flagging less. That distinction is the actual scientific content, so this one probably does earn it.

Rules: no dual axes, no smoothing that is not named in the caption, no truncated y-axis. If a curve is unimpressive, the fix is the caption, not the axis.

## 4. The report

`report/REPORT.md`, generated by `alibi report`, with numbers injected from artifacts rather than typed.

Structure, in this order:

1. **Result, first paragraph.** What was found, what was not resolved, in plain sentences. If the answer is "H1 held, H2 did not resolve at this scale," that is the first sentence. Do not open with method.
2. **Setup.** Model, task, arms, reward, seeds, steps, hardware. Half a page.
3. **The instrument.** Why the oracle is separate from the reward monitor, and how the gap is defined. This is the part that shows the design was thought through, and it is the part a mentor reads closest.
4. **Findings, one subsection per hypothesis,** each labelled held, refuted, or not resolved. No fourth category.
5. **What is not resolved and why.** Seed spread, step budget, model scale, monitor quality. Name the specific thing that would have to change.
6. **Threats to the result.** At least three, written adversarially against the project's own conclusion.
7. **Provenance.** Run ids, config hashes, git revs, what provenance rests on.

Prose rules: no em dashes. Standard terms before local names (say "reward hacking" before "cheat rate", "held-out evaluation" before "oracle"). A reader who knows the field should not have to learn this repo's vocabulary to read the first page.

## 5. README

The README is the surface that decides whether anyone opens anything else. Order:

1. One sentence on what the project does, in plain language, no jargon.
2. The figure.
3. The result in three bullets, including whatever did not work.
4. `alibi verify --no-gpu` with its expected output, so a reader can check the claims immediately.
5. How to reproduce, with the honest compute cost.
6. What this is not: not frontier scale, not novel, not bitwise reproducible on this rollout path.
7. Licenses and citations.
8. The dual-use paragraph.

Section 6 goes above the fold, not in a footnote. Overclaiming is the thing that gets an application binned by someone who reads carefully, and preemptive limitation reads as confidence rather than hedging.

## 6. `alibi verify` output

The command that has to be perfect, because it is the one a mentor runs.

```
alibi verify --no-gpu

reading artifacts/index.json          6 declared runs
checking digests                      6/6 match
recomputing metrics                   
  claim 1  H1 terminal cheat rate a0   published 0.71  computed 0.71  OK
  claim 2  H2 terminal gap a1          published 0.34  computed 0.34  OK
  claim 3  H3 terminal cheat rate a2   published 0.44  computed 0.44  OK
  claim 4  seed spread a1              published 0.09  computed 0.09  OK
figure series                          3/3 match
exit 0
```

Requirements: runs on CPU, no network, under 30 seconds, no dependency beyond the base install. Every published number appears in this output or it is not published.

## 7. What is deliberately absent

No web dashboard. No live training UI. No W&B as a required dependency, since a reader without an account must still be able to check everything. No notebook as the primary interface, because notebooks hide execution order and this project's whole argument is about being checkable.

If there is spare time at the end of the week, it goes into `alibi verify` and the report, not into a UI.
